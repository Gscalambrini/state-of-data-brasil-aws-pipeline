Onde tudo fica, e por quê

Visão geral

Dois pipelines, lado a lado

O mesmo problema (transformar 3 pesquisas em 11 gráficos) foi resolvido duas vezes: uma versão local, em Python puro, para testar a lógica rápido e sem custo; e uma versão real, que rodou de verdade dentro da conta AWS do grupo. O material executivo final usa só os números da versão da AWS — a local existiu para validar a ideia antes de gastar tempo rodando no Glue.

Arquivo por arquivo

As pastas do projeto

Clique em cada pasta para abrir. Cada arquivo tem uma etiqueta dizendo onde ele roda: local roda no seu computador, aws rodou dentro do Glue/Athena, gerado é um arquivo que outro script produz automaticamente (não se edita à mão).

src/ — o código Python que roda fora da AWS▸

Esta pasta mistura duas gerações de código: os scripts que escrevem os notebooks reais (o mais importante do projeto), o protótipo local antigo, e a versão final que usa números reais. Veja a etiqueta de cada um.

build_notebooks.pylocalgera outros arquivos

O arquivo mais importante da pasta. Não é um notebook — é um gerador de notebooks: quando você roda python src/build_notebooks.py, ele escreve os 4 arquivos .ipynb dentro de notebooks/ (Bronze, Silver, Gold, EDA), célula por célula.

Por que existe assim: editar 4 notebooks separados à mão é arriscado — fácil esquecer de aplicar a mesma correção nos 4. Com um gerador único, qualquer bug (como os 2 que apareceram neste projeto) se corrige uma vez aqui e depois se regenera os notebooks com python src/build_notebooks.py de novo.

silver_harmonization.pylocal

Protótipo em pandas da etapa Silver: lê os CSVs de data/raw/ e unifica as 3 edições da pesquisa (que têm colunas diferentes) num formato único.

Por que existe: para testar a lógica de harmonização rapidamente, sem precisar esperar o Spark "ligar" na AWS a cada teste (o cold start leva 1-3 minutos). Os CSVs que ele lê não são exatamente os mesmos arquivos do S3 real — por isso os números daqui divergem um pouco dos números finais.

gold_builder.pylocal

Continuação do script acima: pega o resultado da Silver local e agrega nas 7 tabelas temáticas (mercado, remuneração, gênero, tecnologias, IA...).

eda_charts.pylocal

Gera os 11 gráficos da análise a partir dos números do protótipo LOCAL (silver_harmonization.py + gold_builder.py).

Importante: este NÃO é o script que gerou os gráficos do relatório final — os números aqui são do protótipo, não os reais da AWS.

eda_charts_aws.pylocalgera os PNGs finais

A versão que realmente importa. Gera os MESMOS 11 gráficos que o script acima, só que com os números reais — copiados manualmente, um por um, dos resultados das consultas no Amazon Athena (cada bloco do código cita a pergunta de negócio e a query de onde o número veio, para dar pra conferir).

Por que não só consultar a AWS direto na hora de gerar o relatório: o relatório é montado localmente (próxima seção), e nem sempre há uma sessão AWS ativa disponível — os números reais ficam "congelados" neste arquivo depois de validados uma vez, para o relatório poder ser reconstruído a qualquer momento sem depender da AWS estar online.

viz_style.pylocal

Não gera gráfico nenhum sozinho. Define a paleta de cores (magenta oficial da FIAP) e o estilo visual compartilhado que os dois scripts de gráfico acima importam — garante que todo gráfico do projeto tem a mesma identidade visual.

utils/local

Scripts de bastidor, usados só durante a investigação dos dados: olhar os cabeçalhos de cada CSV, comparar categorias entre as 3 edições, validar a Silver. Não fazem parte do resultado final — são ferramentas de depuração que geraram os relatórios em docs/_headers_*.txt etc.

notebooks/ — o que rodou de verdade dentro da AWS▸

Os 4 arquivos .ipynb aqui são gerados por src/build_notebooks.py — você não edita eles diretamente, edita o gerador e roda ele de novo. Mas foram estes 4 arquivos, carregados um por um no AWS Glue Studio, que viraram os 4 jobs reais.

01_bronze/bronze_glue_notebook.ipynbgeradorodou como job_bronze_tech_challenge

Lê os 3 CSVs brutos do S3 por caminho exato (sem Crawler — ver seção de decisões) e grava 3 tabelas Bronze, uma por edição da pesquisa.

02_silver/silver_glue_notebook.ipynbgeradorodou como job_silver_tech_challenge

A versão PySpark da harmonização — o mesmo raciocínio de silver_harmonization.py, só que lendo as tabelas Bronze reais e rodando dentro do Spark da AWS. É aqui que os dois bugs de mapeamento de coluna e de rótulo de tecnologia foram corrigidos.

03_gold/gold_glue_notebook.ipynbgeradorodou como job_gold_tech_challenge

Agrega a Silver real nas 7 tabelas de negócio.

04_eda/eda_glue_notebook.ipynbgeradorodou como job_eda_tech_challenge

Lê as 7 tabelas Gold reais e desenha os 11 gráficos dentro do próprio notebook da AWS, usando o comando %matplot plt — é a confirmação visual de que os números batem antes de levar para o relatório.

05_analytics_athena/*.sql7 arquivos, rodam no Athena

Não são notebooks — são scripts SQL soltos, um por pergunta de negócio do desafio (q1_estrutura_mercado.sql até q7_oportunidades_e_desafios.sql). Rodam direto no console do Amazon Athena contra as tabelas gold_*.

Bug encontrado e corrigido aqui q4_tecnologias_mais_adotadas.sql filtrava nomes de tecnologia em maiúsculas ('Python'), mas os dados reais são sempre minúsculos ('python') — a consulta rodava sem erro nenhum, só que devolvia zero linhas. Corrigido no arquivo.
presentation/ — a Entrega 1 (material executivo, em PDF)▸

O desafio permite entregar em PowerPoint OU PDF — o grupo trocou de um PowerPoint (poucos slides, principalmente imagens) para um relatório de verdade em PDF (capa, sumário, resumo executivo, introdução, metodologia, análise, diagnóstico, recomendações, conclusão, referências), com bem mais texto e storytelling.

build_relatorio.pylocal, Python

Monta o relatório inteiro em código, usando a biblioteca python-docx: todo o texto, as tabelas e os gráficos (como figuras numeradas, com legenda e fonte) estão escritos aqui, seção por seção. Gera um .docx editável.

Por que não escrever direto no Word: assim, qualquer correção de número (como as que aconteceram nesta mesma sessão) não exige reabrir e editar manualmente um documento de 23 páginas — só mudar o texto/número neste arquivo e rodar python build_relatorio.py de novo.

charts/*.pnggerado por eda_charts_aws.py

As 11 imagens finais que o build_relatorio.py insere como figuras no relatório.

material_executivo.pdfgerado por build_relatorio.py

A Entrega 1 oficial do desafio. O .docx intermediário e a versão anterior em PowerPoint (_obsoleto/) ficam só na máquina local — não fazem parte deste repositório público, que guarda apenas o PDF final e o script que o gera.

diagrams/ — a Entrega 2 (arquitetura)▸
arquitetura_solucao.drawioeditável no app.diagrams.net

A Entrega 2 oficial — o diagrama da arquitetura AWS, desenhado em conjunto com o time diretamente no Draw.io (formato que o desafio pede).

arquitetura_solucao.pngexportado do .drawio

A imagem embutida no relatório (Seção 2). Gerada com o próprio recurso de exportação do Draw.io (Arquivo > Exportar como > PNG) — não por um script separado.

Por que não existe mais um script Python para gerar essa imagem: havia uma versão anterior (_gerar_png.py) que redesenhava o mesmo diagrama do zero em matplotlib, só para produzir um PNG (já que o PowerPoint não conseguia abrir um .drawio direto). Isso criava duas fontes de verdade do mesmo diagrama que podiam ficar dessincronizadas — e de fato ficaram (a versão matplotlib ainda mostrava um tema claro depois que o .drawio já tinha sido redesenhado com tema escuro). Exportar o PNG direto do próprio Draw.io elimina essa duplicação: há só uma fonte de verdade.

data/raw/ — CSVs de referência do protótipo local▸

Raciocínio

As decisões que mais importam

Por que existem dois pipelines inteiros (local e AWS) em vez de um só?

Rodar na AWS tem um custo de tempo real: o Spark demora 1-3 minutos para "ligar" a cada notebook, e o AWS Academy Lab expira a cada 4 horas. Testar a lógica de harmonização em pandas local, no próprio computador, é quase instantâneo. A estratégia foi: acertar a lógica localmente primeiro, "traduzir" ela para PySpark nos notebooks, e só então rodar de verdade na AWS.

O efeito colateral dessa estratégia é que os dois pipelines usam arquivos de origem ligeiramente diferentes (os CSVs de referência locais vs. os CSVs reais do S3), então os números finais divergem um pouco — por isso o material executivo final usa só os números da AWS, nunca os do protótipo local.

Por que não usar um Glue Crawler para a camada Bronze?

Um Crawler é um robô que varre arquivos no S3 e descobre sozinho as colunas. O colega de equipe já tinha criado um, apontando para os 3 CSVs juntos no mesmo prefixo do S3 — só que ele amostrou apenas 1 dos 3 arquivos para adivinhar o formato (as 3 edições têm cabeçalhos diferentes) e aplicou esse formato errado aos 3, gerando uma tabela quebrada com 399 colunas sem nome (col0...col398).

O PDF oficial do desafio nunca menciona a palavra "Crawler" — só pede catalogação "com o Glue Jobs". Por isso, a solução foi fazer o próprio notebook ler os 3 arquivos por caminho exato e se catalogar sozinho, sem depender de nenhum Crawler.

Por que as tabelas novas têm o prefixo tb_?

O colega já tinha criado, no mesmo banco de dados, tabelas chamadas bronze e silver (as quebradas, do Crawler). Para não apagar nem sobrescrever o trabalho dele, as tabelas novas usam nomes diferentes (tb_bronze_*, tb_silver_*) — as duas convivem lado a lado no mesmo banco de dados sem conflito.

Os dois bugs reais encontrados durante a execução

Bug 1 — mapeamento de coluna O código inicial foi escrito olhando os CSVs de referência locais. Quando rodou contra os arquivos reais do S3 (que têm um layout de coluna diferente), o gráfico de "cargo mais comum" misturava cargos de verdade com respostas de outra pergunta (tempo de experiência). Corrigido inspecionando os cabeçalhos reais e reconstruindo o mapeamento de índices em src/build_notebooks.py.
Bug 2 — rótulos de tecnologia crus Depois do bug 1 corrigido, o gráfico de tecnologias mostrava nomes crus de coluna (c_4_c_3_python) em vez de nomes limpos (python). A função que limpa esses nomes só reconhecia o formato dos CSVs locais. Corrigida com uma regex mais geral que cobre os dois formatos reais encontrados no S3.
Dúvidas comuns

Perguntas que você pode estar se fazendo

Se eu quiser só ver o resultado final, que arquivos eu abro?+
Só três: presentation/material_executivo.pdf (a entrega 1), diagrams/arquitetura_solucao.drawio (a entrega 2) e a pasta notebooks/ (a entrega 3). Tudo o que está em src/ é "código de apoio" que produziu essas 3 entregas — você não precisa entender cada linha deles para entregar o desafio.
Por que tem um script "local" e um "aws" fazendo quase a mesma coisa pros gráficos?+
eda_charts.py é o rascunho (números aproximados, do protótipo local). eda_charts_aws.py é a versão final e real (números conferidos no Athena). Se precisar mexer num gráfico do relatório, é sempre o eda_charts_aws.py que você edita.
Onde estão os números que aparecem no relatório?+
Os números dos gráficos (barras, linhas) estão dentro de src/eda_charts_aws.py, em dicionários Python no topo de cada bloco. Os números que aparecem como texto corrido no relatório (tipo "13.057 respondentes") estão em presentation/build_relatorio.py.
O que eu preciso rodar se quiser atualizar alguma coisa?+
Depende do que mudou. Só o texto do relatório → edite build_relatorio.py e rode python build_relatorio.py. Um número de gráfico → edite eda_charts_aws.py, rode com Python, depois rode python build_relatorio.py de novo (ele lê os PNGs mais novos). O diagrama → edite arquitetura_solucao.drawio em app.diagrams.net, exporte como PNG, e rode python build_relatorio.py de novo. Em qualquer caso, depois de gerar o .docx, abra no Word e "Salvar como PDF" para atualizar a entrega oficial (ou automatize via COM/PowerShell, conforme o comentário no topo de build_relatorio.py).
Por que os notebooks dentro de notebooks/ não são editados diretamente?+
Eles são — tecnicamente dá para abrir e editar o .ipynb direto. Mas como os 4 notebooks compartilham muita lógica parecida (cada um lê o resultado do anterior), manter tudo num gerador único (src/build_notebooks.py) evita que uma correção seja aplicada num notebook e esquecida nos outros 3 — foi assim, aliás, que os dois bugs puderam ser corrigidos de forma consistente nas 4 etapas.
